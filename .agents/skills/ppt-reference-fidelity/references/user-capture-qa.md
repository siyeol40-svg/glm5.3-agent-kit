# 사용자 캡처 QA: 결함을 못 찾는 도구를 PASS 판정기로 쓰지 않기

## 실제 문제

캡처를 받았다는 사실, 이미지 분석 tool 호출 성공, 도구의 좋은 평가, 사용자 최종 수용은 서로 다릅니다. 모델이 사진/도형의 의미를 놓치거나 원본을 보고도 잘림을 인지하지 못할 수 있습니다. checklist/JSON/서브에이전트 수를 늘리는 것만으로 정확성이 보장되지 않습니다. 같은 기반 모델이면 서브에이전트라는 이름만으로 독립 검증이 되지 않습니다.

## 검토 전

입력 파일이 실제 tool에 전달됐는지 확인합니다. look_at/looker가 이미지에서 보이는 텍스트와 객체 위치를 구체적으로 기술하지 못하거나 명백한 결함이 있는 합성 테스트를 정상이라 평가하면 capability를 UNVERIFIED/FAILED로 남깁니다. tool의 숨겨진 정답을 미리 알려주는 식의 통과 테스트를 하지 않습니다. 현재 회사 tool의 신뢰성은 이 환경에서 검증하지 못했습니다.

캡처 origin은 user_screenshot입니다. 다른 문서의 오래된 캡처를 재사용하지 않습니다. 사용자가 주신 revision/슬라이드/영역 표기를 확인합니다. 전체 캡처에서 작은 글자를 판정하지 않고 필요한 상세 캡처를 요청합니다. export가 금지돼서 캡처를 받는 상황에서 자동 screenshot이나 PDF 변환을 대체 경로로 시도하지 않습니다.

## 의견 형식

각 발견은 region/object → 관찰한 사실 → 기대 기준 → 차이 → 수정 제안으로 기록합니다. "좋아 보임/문제 없음"만 쓰지 않습니다. 창의적이라는 주관적 칭찬 대신 새 시각 자료가 어떤 메시지를 전달하는지 설명합니다.

불확실함은 NOT REVIEWED입니다. 도구가 입력을 읽지 않았거나 보지 못한 결함을 코드 검사라고 포장하지 않습니다. COM readback으로 확인되는 문구 누락·객체 치수 차이는 직접 검사하고, 사진의 의미·가림·전체 인상은 캡처와 사용자 의견으로 분리합니다.

## 사용자 지적의 우선순위

사용자가 "사진이 이전 자료 그대로", "제목이 잘림", "문장만 옮김"이라고 지적하면 known_issues.json에 그대로 보존하고 해당 항목을 재현합니다. 모델의 이전 PASS나 "의도적 차별화" 주장으로 반박하며 닫지 않습니다. 수정 전/후와 새 파일 revision을 연결하고 실제 사용자 확인 전에는 RESOLVED로 기록하지 않습니다.

도구 검토가 계속 결함을 놓치면 자동 최종 판정 역할에서 제외합니다. 객관적 검사와 사용자 수동 검토를 유지하고 tool 의견은 참고로만 제공합니다. 최종 수용은 실제 사용자 메시지에 근거합니다. 이 단계는 작업 권한을 다시 묻는 절차가 아니라 구체적인 결과물에 대한 품질 확인입니다.

## 한계

사용자가 캡처를 제공해도 잘못된 사진 선택이나 메시지 구성까지 도구가 잘 이해한다고 보장할 수 없습니다. 그래서 content_blueprint와 visual_implementation을 편집 전에/후에 별도로 확인합니다. 사진 교체 로그도 최종 삽입된 이미지의 의미를 완전히 증명하지 못합니다. 사용자 수용을 포함한 제한적 품질 확인으로 보고하며, 미수행 ZIP/자동 렌더 검사를 PASS로 채우지 않습니다.
